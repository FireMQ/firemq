# FireMQ language bindings

Clients for Python, Kotlin, Swift, Ruby, C and Dart, built on the Rust client
(`crates/firemq-client`) through `crates/firemq-client-ffi`. That crate exposes two surfaces:

- A [UniFFI](https://mozilla.github.io/uniffi-rs/) object API, from which the Python, Kotlin,
  Swift and Ruby code is generated.
- A C ABI, described by [`c/firemq.h`](c/firemq.h), used by C, C++ and Dart.

Both are blocking: each call runs on one shared multi-threaded Tokio runtime and returns when
the broker answers. Message headers and queue or binding arguments cross the boundary as JSON
objects. Defaults match the Rust client: durable queues and exchanges, persistent messages, and
publishes that wait for the broker's confirm.

| Language | Directory | Built with | Notes |
|---|---|---|---|
| Python | [`python`](python) | maturin (`bindings = "uniffi"`) | Pythonic wrapper: `firemq.connect()`, context managers, iterable subscriptions |
| Kotlin | [`kotlin`](kotlin) | Gradle, JNA | `Client.close` is named `disconnect`, since `close()` frees the native object (`AutoCloseable`) |
| Swift | [`swift`](swift) | SwiftPM | Links `libfiremq_client_ffi`; `build-xcframework.sh` packages it for apps (needs Xcode) |
| Ruby | [`ruby`](ruby) | gem, `ffi` | `FireMQ.connect`, `FireMQ::Error` subclasses, `Enumerable` subscriptions |
| C | [`c`](c) | make | Header generated by cbindgen; ownership rules at the top of the header |
| Dart | [`dart`](dart) | pub, `dart:ffi` | Over the C API; native handles freed by `NativeFinalizer` |

## Install

| Language | Package |
|---|---|
| Python | `pip install firemq` |
| Ruby | `gem install firemq` |
| Swift | the Swift package [FireMQ/firemq-swift](https://github.com/FireMQ/firemq-swift), which uses the XCFramework from each release |
| Dart | `dart pub add firemq`, plus the C library from a release (see [`dart/README.md`](dart/README.md)) |
| C, C++ | the `firemq-ffi-<target>` archives on the [releases page](https://github.com/FireMQ/firemq/releases) (see [`c/README.md`](c/README.md)) |
| Kotlin | not published yet: it is meant for Android, which needs an AAR. On the JVM, use `firemq-kotlin` from [FireMQ/firemq-java](https://github.com/FireMQ/firemq-java) |

[RELEASING.md](../RELEASING.md) describes how they are built and published.

## The API

Every binding has the same shape:

- `Client.connect(url)`, `close()`
- `declare_queue(name, durable, exclusive, auto_delete, args)` returning `{name, messages, consumers}`
- `delete_queue`, `purge_queue` (both return a message count), `declare_exchange`,
  `delete_exchange`, `bind_queue`, `unbind_queue`, `bind_exchange`
- `publish(exchange, key, body, options)` with `persistent`, `mandatory`, `confirm`,
  message properties and headers
- `subscribe(queue, prefetch, no_ack)` returning a subscription with `next(timeout)` and
  `cancel()`; `next` returns nothing on timeout and fails with `Closed` once the subscription
  has ended
- `get(queue, no_ack)`
- deliveries with the body, exchange, routing key, `redelivered`, properties, headers,
  `ack()` and `nack(requeue)`

Errors are `Server {code, message}` (the broker refused a request; `code` is an AMQP reply code
such as 403, 404 or 406), `Unroutable`, `Nacked`, `Closed` and `Other`.

## Regenerating

The Kotlin, Swift and Ruby sources and the C header are checked in. After changing the FFI
crate, run:

```bash
cargo install cbindgen --locked   # once
bindings/generate.sh
```

CI fails when the checked-in files are stale. Python's module is generated by maturin at build
time.

## Testing

Start a broker, then run each binding's tests. They connect to `$FIREMQ_URL`
(default `fire://guest:guest@localhost:5673`).

```bash
cargo run -p firemq -- --ephemeral &
cargo build -p firemq-client-ffi --release

# Python
(cd bindings/python && uv venv && uv pip install maturin pytest \
  && source .venv/bin/activate && maturin develop && pytest)

# Kotlin; FIREMQ_LIB_DIR=<dir> picks another library
(cd bindings/kotlin && gradle test conformanceDriver)

# Swift
(cd bindings/swift && swift build -Xlinker -L../../target/release \
  && DYLD_LIBRARY_PATH=../../target/release .build/debug/hello-firemq)

# Ruby (libfiremq_client_ffi.dylib on macOS)
export FIREMQ_LIB=$PWD/target/release/libfiremq_client_ffi.so
(cd bindings/ruby && bundle install && bundle exec ruby -Ilib -Itest test/test_firemq.rb)

# Dart, over the C API; also reads FIREMQ_LIB
(cd bindings/dart && dart pub get && dart test)

# C
(cd bindings/c && make run PROFILE=release)
```

Every binding except C has a conformance driver for the SDK suite in
[`spec/conformance.md`](../spec/conformance.md). The runner starts its own broker:

```bash
conformance() { cargo run -q -p firemq-conformance -- run --driver "$1"; }
conformance "bindings/python/.venv/bin/python bindings/python/conformance_driver.py"
conformance bindings/kotlin/build/conformance-driver
conformance bindings/swift/.build/debug/firemq-conformance-driver
conformance "cd bindings/ruby && bundle exec ruby -Ilib conformance_driver.rb"
conformance "cd bindings/dart && dart run tool/conformance_driver.dart"
```

## Packaging

Not done yet; each step needs registry credentials or a platform toolchain:

- **Python**: wheels per platform with `maturin build --release` (for example with
  `PyO3/maturin-action`), then upload to PyPI.
- **Kotlin**: bundle `libfiremq_client_ffi` per platform as JNA resources
  (`linux-x86-64/`, `darwin-aarch64/`, ...) and publish to Maven Central.
- **Swift**: `swift/build-xcframework.sh` builds `FireMQFFI.xcframework` on a Mac with Xcode
  (the workflow runs it on demand); a release would attach it and switch `Package.swift` to a
  `binaryTarget`.
- **Ruby**: copy the library into `ruby/lib/firemq/` per platform and build platform gems for
  rubygems.org.
- **Dart**: publish to pub.dev with the library shipped through native assets or installed
  separately.
